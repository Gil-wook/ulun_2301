# 설치 없이 GitHub에서 uLaunch 개발 빌드하기

PC나 Replit에 devkitPro를 설치하지 않고 GitHub 서버에서 빌드하는 방법입니다.
필요한 것은 GitHub 계정과 저장소 하나입니다. 이 설정은 GitHub.com의 Actions용입니다.

**현재 포팅은 검증되지 않은 개발 단계입니다. 빌드가 성공하더라도 23.0.1에서 실행된다는 보장은 없습니다.**

## 첫 원격 빌드 결과

2026-10-23 KST에 [GitHub Actions 실행이 성공했습니다](https://github.com/Gil-wook/ulun_2301/actions/runs/39831164539).
네 가지 Switch 컴포넌트와 개발 ZIP·대응 소스가 생성되었고, 다운로드 후 무결성 검사도 통과했습니다.
실행 정보와 체크섬은 [검증 기록](build-verification.ko.md)을 참고하세요. 실기기 실행은 아직 검증하지 않았습니다.

## 1. GitHub 저장소 만들기

1. GitHub에 로그인합니다.
2. 새 저장소를 만듭니다. 예를 들어 이름을 `ulaunch-build`로 지정합니다.
3. 생성 화면에서 README 추가를 선택해 빈 저장소가 되지 않도록 합니다.

이 Replit 프로젝트 전체나 uLaunch 소스 전체를 업로드할 필요는 없습니다.
아래 설정 파일 하나가 공식 소스와 필요한 공개 라이브러리를 자동으로 가져옵니다.

## 2. 설정 파일 하나 올리기

1. 이 프로젝트의 `.github/workflows/build-ulaunch.yml`을 열고 전체 내용을 복사합니다.
2. GitHub 저장소의 **Add file → Create new file**을 선택합니다.
3. 파일 이름에 **`.github/workflows/build-ulaunch.yml`**을 입력합니다.
4. 내용을 붙여넣고 **Commit changes**로 기본 브랜치에 저장합니다.

`.yml` 파일의 들여쓰기를 그대로 유지하세요. Markdown 코드 블록 표시(` ``` `)는 붙이지 않습니다.
이미 이 프로젝트를 GitHub에 연결해 사용하고 있다면 이 파일을 기본 브랜치에 반영하면 됩니다.

## 3. 버튼으로 실행하기

1. 저장소의 **Actions** 탭을 엽니다.
2. Actions 활성화 안내가 나오면 활성화합니다.
3. 왼쪽의 **Build uLaunch 23.0.1 (experimental)**을 선택합니다.
4. **Run workflow → Run workflow**를 누릅니다.

Run workflow 버튼이 없다면 파일이 기본 브랜치에 저장되었는지, Actions가 활성화되어 있는지 확인하세요.
조직 저장소에서는 외부 Actions와 공식 devkitPro 컨테이너 사용이 조직 정책으로 제한될 수 있습니다.

개인 API 키나 Nintendo 키, 콘솔 펌웨어 파일은 필요하지 않습니다.
직접 키를 입력하거나 보안 검증을 끌 필요도 없습니다.
GitHub Actions 이용 가능 여부와 사용량 제한은 GitHub 계정·저장소 설정에 따라 달라집니다.

## 4. 결과 받기

실행이 끝나면 해당 실행 페이지 아래쪽 **Artifacts**를 확인합니다.

- **`uLaunch-23.0.1-dev-숫자`**: 성공한 경우에만 생성됩니다.
  - `uLaunch-23.0.1-dev.zip`: 네 가지 Switch 컴포넌트의 개발 빌드.
  - `uLaunch-23.0.1-dev-source.tar.gz`: 수정된 소스와 종속 라이브러리 소스·라이선스.
  - `BUILD-INFO.txt`: 소스 버전, 검증 한계, 빌드 정보.
  - `sdk-packages.txt`: 실제 사용한 SDK 패키지 버전.
  - `port-baseline.patch`: 원본 대비 개발 버전·라이브러리 변경.
  - `SHA256SUMS.txt`: 빌드 ZIP과 소스 압축 파일의 체크섬.
- **`build-logs-숫자`**: 실패한 경우에도 가능한 범위에서 저장됩니다.

GitHub에서 받은 바깥쪽 ZIP을 먼저 풀면 안에 개발 빌드 ZIP과 소스 압축 파일이 있습니다.
Artifacts는 14일 보관하도록 설정되어 있으며 저장소 정책에 따라 실제 보관 기간이 제한될 수 있습니다.

실패하면 빨간색 단계의 로그 또는 `build-logs` 압축 파일을 공유해 주세요.
실행 환경이 시작되기도 전에 실패했거나 실행이 강제 취소되었다면 Artifacts가 없을 수 있습니다.
이 경우 실행 페이지의 오류 내용을 확인합니다.

## 이 설정이 하는 일

- 공식 uLaunch의 22.5.0 대응 소스를 고정된 버전으로 가져옵니다.
- Atmosphere-libs를 23.0.1 버전 지원이 추가된 소스로 변경합니다.
- 표시 버전을 1.2.6 개발 빌드로 변경합니다. 공식 1.2.6 릴리스가 아닙니다.
- 고정된 libnx 소스를 빌드합니다.
- 원본이 권장하는 SDL2 2.28.5-3의 소스와 패치를 체크섬으로 확인하고 다시 빌드합니다.
- 오류 코드 헤더는 고정된 로컬 소스로 생성해 GitHub API 호출 제한을 피합니다.
- uSystem, uLoader, uMenu, uManager를 빌드합니다. Java PC 도구인 uScreen과 테마 편집기 uDesigner는 제외합니다.
- 결과 파일이 모두 존재하는지 확인한 뒤 압축합니다. 부분 빌드를 정상 결과로 내보내지 않습니다.
- 설치·배포나 콘솔 업데이트는 하지 않습니다.

소스 버전과 컨테이너는 고정되어 있으며, SDK는 해당 공식 이미지에 포함된 패키지 스냅샷을 사용합니다.
필수 SDK 그룹과 도구가 없으면 즉시 실패하며, 패키지 서버 접속 실패를 숨기거나 서명 검증을 끄지 않습니다.
실제 SDK 버전은 로그와 결과물에 기록됩니다. 빌드 시각 등이 포함되므로 바이트 단위 재현성까지 보장하지는 않습니다.
`sdk-packages.txt`는 이미지에 설치된 패키지 데이터베이스 기록입니다. 이후 소스에서 다시 빌드해 덮어쓴
libnx와 SDL2는 이 기록만으로 버전을 판단하지 말고 `BUILD-INFO.txt`의 소스 커밋·레시피와 개별 빌드 로그를 함께 확인하세요.

## 이후 소스 수정 시 주의

이 설정은 현재 포팅의 **라이브러리 버전 변경과 개발 버전 표시**를 재현합니다.
Replit 안의 `third_party/ulaunch-source`를 업로드하거나 빌드하는 것이 아닙니다.
나중에 C++ 소스를 추가로 수정하면 그 수정도 워크플로에 반영해야 합니다.

## 현재 검증 범위

첫 원격 실행은 SDK 패키지 서버의 HTTP 403으로 실패했고, 고정 이미지의 SDK 스냅샷을 사용하도록 수정한 다음 실행은 성공했습니다.
이는 해당 소스·SDK 조합의 컴파일과 패키징을 확인한 것이며, 다른 환경이나 앞으로의 소스 변경까지 보증하지 않습니다.
실제 콘솔에서는 홈 메뉴 진입, 앱 실행·복귀, 테마 읽기, 절전·복귀 등을 별도로 확인해야 합니다.
검증되지 않은 빌드를 유일한 SD 카드 사본에 덮어쓰지 마세요.

원본과 종속 라이브러리의 라이선스·고지는 유지합니다.
수정된 빌드를 다른 사람에게 배포할 때는 해당 실행의 대응 소스도 함께 제공하고 라이선스 의무를 확인하세요.

## 다운로드한 결과물 검증

개발용 도구 `scripts/verify-ulaunch-release.py`는 다운로드한 Artifacts의 바깥쪽 ZIP을 푼 폴더를 검사합니다.
Python 3.11 이상에서 추가 패키지 없이 실행할 수 있으며, 빌드 파일을 실행하거나 소스 압축을 풀지는 않습니다.

```sh
python3 scripts/verify-ulaunch-release.py 다운로드폴더 \
  --run-url https://github.com/소유자/저장소/actions/runs/실행번호
```

체크섬 두 개, ZIP CRC, 필수 Switch 바이너리 10개의 파일 형식, uSystem 사본 일치,
실행 URL, 라이선스, 대응 소스와 SDL2 입력 파일, 개발 버전을 확인합니다.
이 검사는 파일의 무결성과 구성만 확인하며 콘솔 실행 검증을 대신하지 않습니다.

검증 도구 자체의 누락·손상 검출 테스트:

```sh
python3 -m unittest discover -s scripts/tests -v
```
